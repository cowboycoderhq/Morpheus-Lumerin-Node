TEE (Trusted Execution Environment) verification on Morpheus is a **two-hop chain**, with each hop attested separately. The on-chain `tee` tag on a model triggers both hops:

```
C-Node (v6.0.0+) ─Phase 1─▶ P-Node -tee image (v7.0.0+) ─Phase 2─▶ Backend LLM (SecretVM)
```

- **Phase 1** is what the **consumer's proxy-router** runs against the provider's P-Node.
- **Phase 2** is what the **provider's P-Node (v7.0.0+)** runs against its own backend LLM. The consumer never sees Phase 2 directly.
- A v6.0.0+ consumer paired with a v7.0.0+ provider gets the full chain transparently — **no consumer-side upgrade is needed** to benefit from Phase 2.

## What Phase 1 proves

When a v6.0.0+ C-Node opens a session for a `tee`-tagged model, the consumer's proxy-router proves the following about the provider's P-Node, at session open and on every prompt:

- The proxy-router binary is the exact binary built by the official CI/CD from a known commit (verified via cosign signature on the `-tee` image).
- The signed manifest records the image's chat-context setting: `PROXY_STORE_CHAT_CONTEXT=false` (`proxy-router/Dockerfile.tee:23`, surfaced as `baked_env`). That is a Docker `ENV` default and the manifest describes the **image**, not the container's live environment — see "What it does *not* prove".
- The signed manifest records the image's logging pins: `LOG_IS_PROD=true`, `LOG_LEVEL_APP=info`, and `warn` on the TCP, RPC and storage loggers (`proxy-router/Dockerfile.tee:30-36`, surfaced as `baked_env`; the publish job refuses to ship a manifest whose Dockerfile bakes `LOG_LEVEL_APP=debug`, `.github/workflows/build.yml:814-823`). These too are `ENV` defaults read off the image at build time, not a reading of the running process.
- The signed manifest records the blockchain config the image was built with — contracts, chain ID and blockscout URL for the target network (`proxy-router/Dockerfile.tee:13-16`, surfaced as `baked_env`). Same standing as the two above: a build-time record, not a runtime guarantee.
- The image has not been tampered with (RTMR3 replay of the published deployed compose against the live TDX quote).
- The TLS certificate terminating the **attestation** connection — the `:29343/cpu` fetch the consumer makes — is pinned into the quote's `reportData[0:32]`, so no TLS-terminating proxy or CDN can sit in that path. Prompts do not travel over that connection; see "What it does *not* prove" below.
- A ~50 ms fast path (quote hash + TLS fingerprint compare) re-checks on every prompt; any drift triggers full re-verification.

## What Phase 2 proves

Phase 2 runs **entirely inside the provider's P-Node**. For each `tee`-tagged model, the v7+ P-Node proves the following about the backend LLM at startup and on every prompt:

- Backend's CPU TDX quote is independently verified (`AttestBackend` at startup, `FastVerifyBackend` per prompt). The attestation endpoint is resolved from the model's `apiUrl` host by probing `:21434` (current SecretAI backends, where a host-net Caddy fronts the evidence endpoints) and falling back to `:29343` (standard SecretVMs with attest-rest bound directly).
- A digest of the backend's TLS certificate is pinned into the CPU quote's `reportData[0:32]` — SHA-256 of the certificate's SPKI on current SecretVMs, or of the full certificate on legacy VMs. Either binding is accepted, so a mixed fleet stays verifiable, and a certificate renewal that keeps the TEE-resident key triggers re-attestation rather than an outage.
- Backend's GPU attestation nonce is bound to the CPU quote via `reportData[32:64]`; GPU evidence is independently verified by **NVIDIA NRAS**. NRAS verification is mandatory — a failed or unreachable NRAS fails the attestation.
- Backend's `docker-compose.yaml` is recovered from the attestation endpoint (raw bytes or the legacy HTML-wrapped form — both are tolerated) and **RTMR3 is replayed** against the live TDX quote — proving the compose the backend reports is the one measured into its own quote. This does **not** anchor which models that compose ought to declare: the expected RTMR3 is recomputed from the file the backend serves, and no per-model golden value exists. See [what is actually proven today](/providers/full/tee-backend-verification#what-is-actually-proven-today).
- MRTD + RTMR0-2 are looked up in the published SecretVM TDX artifact registry to confirm firmware/VM/kernel/initramfs.
- Per-model attestation state is exposed on `GET /v1/models/attestation` for monitoring and forensics.

## What it does *not* prove

- It does **not** prove the *quality* of the model's output. TEE attests the *software*, not the *answer*.
- It does **not** prove the model wasn't fine-tuned in a problematic way before being baked into the backend image.
- It does **not** prove anything about non-TEE (untagged) providers. A non-`tee` model has no attestation chain at all.
- It does **not** protect the inference connection itself on the Phase 2 hop. The certificate digest in `reportData[0:32]` binds only the attestation probe connection the P-Node opens to `/cpu`; the connection that actually carries prompts and completions to the backend is not pinned (`PinnedHTTPClient` exists but has no production caller — `aiengine/ai_engine.go:64` passes `nil`, so a plain client is used). A TLS-terminating CDN or reverse proxy in front of the backend would therefore not be detected, and inference data could be intercepted there. See [TEE backend verification](/providers/full/tee-backend-verification).
- It does **not** keep the prompt confidential on the Phase 1 hop either. Prompts do not travel over the pinned attestation connection: the consumer dials the provider's morrpc port over plain TCP with no TLS at all (`proxyapi/proxy_sender.go:571`, `:822`; the provider listens with `net.Listen("tcp", ...)` at `repositories/transport/tcp_server.go:39`), and the request payload is signed but not encrypted (`morrpcmessage/mor_rpc.go:471-497`, whose `providerPubKey` argument is unused — the receiver consumes `[]byte(req.Message)` at `proxyapi/controller_morrpc.go:194`). Only the provider's *response* is ECIES-encrypted to the consumer's public key (`proxyapi/proxy_receiver.go:335`). An on-path observer between consumer and P-Node therefore cannot forge a request undetected or read a completion, but can read the prompt.
- It does **not** prove that the running container's environment matches the manifest's `baked_env`. Those are Docker `ENV` defaults, and the deployed compose declares `env_file: - usr/.env` (`proxy-router/docker-compose.tee.yml:15-16`) — the file SecretVM fills from the operator's encrypted-secrets input. RTMR3 is the replay of the compose bytes and the rootfs digest and nothing else (`proxy-router/internal/attestation/rtmr.go:12`), so the *reference* to that file is measured while its *contents* are not, and Docker precedence puts `env_file` above the image's `ENV`. Any baked value the compose does not also name in its `environment:` block — chat-context storage, every `LOG_*`, `ENVIRONMENT`, the blockchain settings — can therefore be set from that file with the measurement unmoved, and nothing downstream re-forces it: the config loader reads every `env:`-tagged field straight from the process environment with no allowlist (`proxy-router/internal/config/loader.go:54-61`), the entrypoint is a bare `proxy-router` (`proxy-router/Dockerfile.tee:45`), and `baked_env` is parsed into a `json.RawMessage` that no code reads (`proxy-router/internal/attestation/golden.go:48`). What the measurement *does* foreclose is editing the compose itself: an `environment:` entry re-enabling storage, or any other byte, changes RTMR3 and the consumer's replay fails.
