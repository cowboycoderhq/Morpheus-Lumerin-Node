The proxy-router is configured through `.env` (or container env vars). This page documents most variables consumed by the proxy-router, including Docker-related environment variables. It omits IPFS_DISABLED, IPFS_MULTADDR, and MULTICALL3_ADDR (defined in config.go). The canonical `.env.example` lives in the repo at [`proxy-router/.env.example`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/.env.example) and the annotated dump (which is complete) at [`docs/proxy-router.all.env`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/docs/proxy-router.all.env).

## Conflicting / overlapping variables in the proxy-router — read this first

Several of the proxy-router's variables look like they do "the same thing." They don't. The proxy-router resolves each pair with a specific precedence rule, and getting it wrong is a common cause of "I changed the env but nothing happened."

<Warning>
For the `*_CONTENT` ↔ `*_PATH` pairs listed below, the **`*_CONTENT`** variable is a **one-shot file seeder** (except for `RATING_CONFIG_CONTENT`, which is a fallback if the file cannot be read). For the seeder pairs, it only takes effect when the corresponding file **does not exist**. After the first successful start the file exists, and changing the `*_CONTENT` env on subsequent runs has **no effect** until you delete the file at `*_PATH`.

**A loader returning an error is not the same as the router exiting.** Each `*Loader.Init` below returns a Go error when its file is missing, but whether that error stops startup is decided by the call site in [`proxy-router/cmd/main.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/cmd/main.go), not by the loader. For the models and agent pairs `proxy-router/cmd/main.go:311-321` logs the error at **warn** level and carries on with an empty set. The rating config never reaches that decision on a missing file: `LoadRating` swallows the read error itself, falls back, and returns no error, so **a missing — or malformed — rating file starts the router too** (`proxy-router/internal/config/rating_config.go:36-47`). What exits non-zero at `proxy-router/cmd/main.go:277-280` is a rating config that was successfully *chosen* and then rejected by the parser: a malformed `RATING_CONFIG_CONTENT`, an unrecognised `algorithm`, or no `algorithm` key. Read the call site before concluding a missing file is fatal, and read the `RATING_CONFIG_PATH` section below before concluding a malformed one is.
</Warning>

### `COOKIE_FILE_PATH` ↔ `COOKIE_CONTENT`

| Situation | What the proxy-router does |
|-----------|---------------------------|
| File at `COOKIE_FILE_PATH` already exists | Reads the file. **`COOKIE_CONTENT` is silently ignored.** |
| File does not exist + `COOKIE_CONTENT` is set | Writes `COOKIE_CONTENT` to the file (`username:password\n`), then reads it. |
| File does not exist + `COOKIE_CONTENT` is unset | Generates a random 32-char password for `admin`, writes it to the file. |
| File does not exist + `COOKIE_CONTENT` has no `:` separator | **Hard startup failure.** `EnsureConfigFilesExist` returns `invalid cookie content` (`auth.go:222-224`) and `main.go:222-224` returns it, so the process exits non-zero. `COOKIE_CONTENT` must be `username:password`, not a bare password. |

Source: [`proxy-router/internal/system/auth.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/internal/system/auth.go) (`EnsureConfigFilesExist`).

**Practical implications**

- For TEE / Akash / ephemeral container deployments, set `COOKIE_CONTENT` once on first start; the file gets seeded inside the volume and persists.
- To rotate credentials on a self-hosted node, use the **`POST /auth/users` endpoint** (or edit the cookie file in place) — changing `COOKIE_CONTENT` after first start does nothing.

### `MODELS_CONFIG_PATH` ↔ `MODELS_CONFIG_CONTENT`

| Situation | What the proxy-router does |
|-----------|---------------------------|
| File at `MODELS_CONFIG_PATH` already exists | Reads the file. **`MODELS_CONFIG_CONTENT` is silently ignored.** |
| File does not exist + `MODELS_CONFIG_CONTENT` is set | Writes `MODELS_CONFIG_CONTENT` to the file, then reads it. |
| File does not exist + `MODELS_CONFIG_CONTENT` is unset | `ModelConfigLoader.Init` returns `models config file not found` (`models_config.go:85`) — but the proxy-router **starts anyway**. `main.go:311-315` logs `failed to load model config, running with empty` at **warn** level and continues; no later exit is gated on it. The node comes up healthy, answers `/healthcheck`, and serves **zero models**. |

Sources: [`proxy-router/internal/config/models_config.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/internal/config/models_config.go) (`ModelConfigLoader.Init`, which produces the error) and [`proxy-router/cmd/main.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/cmd/main.go) lines 311-315 (which decides what happens to it).

**Practical implications**

- Use `MODELS_CONFIG_CONTENT` (single-line JSON) in TEE/Akash deployments where you can't mount a volume.
- To update models on a self-hosted node, edit the JSON file directly and restart — don't bump `MODELS_CONFIG_CONTENT`. See [models-config.json](/reference/models-config).
- **Do not use "the process is up" as evidence that your models loaded.** A missing, unreadable, or malformed `models-config.json` produces one warn line and a running router with an empty model set — not a crash-loop. Confirm the models are actually there with `GET /healthcheck` (the `models` array), and grep the startup log for `failed to load model config, running with empty`. Do **not** rely on the `models config loaded from file` info line as the all-clear — `models_config.go:98` emits it before the format is validated, so it also appears on a config that is then rejected.

### `AGENT_CONFIG_PATH` ↔ `AGENT_CONFIG_CONTENT`

Same `*_CONTENT`-only-seeds-the-file rule as the two above. Leaving `AGENT_CONFIG_PATH` unset does not disable the loader — it falls back to `agents-config.json` in the working directory. If that file is absent and `AGENT_CONFIG_CONTENT` is unset, `AgentConfigLoader.Init` returns `agents config file not found` (`agents_config.go:71`) — but, exactly as with the models pair, `main.go:317-321` downgrades that to a warning and **the router starts with an empty agent set**. Sources: [`proxy-router/internal/config/agents_config.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/internal/config/agents_config.go) (the loader) and [`proxy-router/cmd/main.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/cmd/main.go) lines 317-321 (the call site).

### `RATING_CONFIG_PATH` ↔ `RATING_CONFIG_CONTENT`

`RATING_CONFIG_CONTENT` is used as a fallback if the file at `RATING_CONFIG_PATH` cannot be read; it does **not** create or modify the file. If the file is unreadable **and** `RATING_CONFIG_CONTENT` is unset, `LoadRating` falls back to a built-in default config (`default` algorithm, empty allowlist) and logs `failed to load rating config file, using defaults` — a missing rating config is **not** fatal (`rating_config.go:36-47`).

The inversion against the models/agent pairs is narrower than it looks, so take it in two steps.

**Step 1 — choosing the text.** Missing, unreadable and *malformed* all fail identically here: `lib.ReadJSONFile` validates the bytes as JSON before returning them (`proxy-router/internal/lib/json.go:46-50`), so a typo is indistinguishable from a missing file and takes the same fallback branch (`proxy-router/internal/config/rating_config.go:37-44`). **A malformed `rating-config.json` does not take the node down.** It starts on `RATING_CONFIG_CONTENT`, or on `RatingConfigDefault` — empty `providerAllowlist`, **no denylist**, i.e. allow-all (`proxy-router/internal/config/rating_config.go:10-25`). A denylist you rely on to avoid paying certain providers therefore disappears on a stray comma while the node stays up and healthy, so **never read "it started" as "my rating config parsed"**; read the warn line `failed to load rating config file, using defaults`, then check for `provider filtering is enabled` vs `provider filtering is disabled` (`proxy-router/internal/rating/rating_factory.go:69-86`).

**Step 2 — parsing the chosen text.** Whatever step 1 settled on is parsed by `rating.NewRatingFromConfig`, and three outcomes exit non-zero through `proxy-router/cmd/main.go:277-280`: a malformed `RATING_CONFIG_CONTENT` that was used because the file was unreadable; an `algorithm` that is present but unrecognised; and a config with **no** `algorithm` key — the empty string matches no `case`, and the error reads `unknown rating algorithm:` with nothing after the colon (`proxy-router/internal/rating/rating_factory.go:100-117`). Sources: [`proxy-router/internal/config/rating_config.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/internal/config/rating_config.go) and [`proxy-router/cmd/main.go`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/proxy-router/cmd/main.go) lines 277-280.

### `AUTH_CONFIG_FILE_PATH` (no inline twin)

Path to `proxy.conf`, which holds `rpcauth=` and `rpcwhitelist=` lines. **There is no `AUTH_CONFIG_CONTENT` env** — the file is built at runtime by the proxy-router itself when you add users via [`POST /auth/users`](/reference/api-auth#add-or-update-a-user). For TEE / ephemeral deployments, `proxy.conf` is created on first start (with the admin entry derived from the cookie file) and managed via the API afterwards.

### `WALLET_PRIVATE_KEY` ↔ system keychain

| Situation | What the proxy-router does |
|-----------|---------------------------|
| `WALLET_PRIVATE_KEY` is set | Uses it. The keychain is **not** read. |
| `WALLET_PRIVATE_KEY` is unset | Reads / writes the key from the OS credential store. **This is not macOS-only:** `proxy-router/internal/repositories/keychain/keychain.go:6` uses `github.com/zalando/go-keyring`, which ships macOS Keychain, Windows Credential Manager and Linux/BSD Secret Service backends, and `proxy-router/cmd/main.go:259-266` has no platform guard. |
| `WALLET_PRIVATE_KEY` unset **and** the platform has no credential-store backend (go-keyring falls back to `unsupported platform`) | Refuses to start signing transactions; read-only operations still work. |

`APP_RESET_KEYCHAIN=true` is a **one-shot maintenance wipe, not a startup modifier**, and it does not read "reset, then start." It deletes the stored wallet and the stored ETH-node URLs and then **returns before the node is built**: `proxy-router/cmd/main.go:198` is a bare `return nil` inside the block opened at `:181`, while everything that constructs storage, the RPC client and the HTTP server begins at `:204`. Because the return value is `nil`, `proxy-router/cmd/main.go:47-53` exits **0** — no error text, no listening port, and nothing a supervisor's failure detection can catch. Leave the variable set in a Compose file, a Kubernetes manifest or a systemd unit and every start is an immediate clean exit that reads as success. Run it once by hand, then unset it. The wipe is also not macOS-specific — see the credential-store note above.

### `WEB_PUBLIC_URL` fallback

If `WEB_PUBLIC_URL` is unset, the proxy-router derives it from `WEB_ADDRESS`, and the substitution is narrower than "falls back to localhost": `proxy-router/internal/config/config.go:183-190` prepends `http://` and rewrites the host to `localhost` **only** when `WEB_ADDRESS` is a bare `:port` or contains `0.0.0.0`. Any host that does not contain the substring `0.0.0.0` is preserved verbatim — `WEB_ADDRESS=192.168.1.5:8082` yields `http://192.168.1.5:8082`, not a loopback URL. The rewrite is a plain `strings.Replace` (`:188`), not a host-equality test, so a host that merely *contains* the substring is rewritten too: `0.0.0.0.nip.io:8082` becomes `http://localhost.nip.io:8082`. Either way the result is a LAN, container or loopback address that consumers on the internet cannot reach. For provider deployments where consumers must reach you over the public internet, **always set this explicitly** to your public URL (e.g. `https://provider.example.com`). The TLS-pinning step in TEE attestation reads this URL.

### `ETH_NODE_USE_SUBSCRIPTIONS` ↔ `ETH_NODE_POLLING_INTERVAL`

Not a precedence pair, but easy to misconfigure:

- `ETH_NODE_USE_SUBSCRIPTIONS=true` → expects a **WSS** `ETH_NODE_ADDRESS` (e.g. `wss://...`). Polling interval is irrelevant.
- `ETH_NODE_USE_SUBSCRIPTIONS=false` (default) → expects an **HTTPS** `ETH_NODE_ADDRESS` and uses `ETH_NODE_POLLING_INTERVAL` (default `10` seconds).

Mismatch (e.g. `subscriptions=true` with HTTPS endpoint) makes the node fail to receive blockchain events even though startup may look healthy.

### `PROXY_STORE_CHAT_CONTEXT` in the `-tee` image

The `-tee` image sets `PROXY_STORE_CHAT_CONTEXT=false` as a Docker `ENV` default (`proxy-router/Dockerfile.tee:23`), so that is the value you get unless something supplies another one. It is **not** immutable at the image level: an `ENV` default is overridden by `docker run -e`, by a Compose `environment:` entry, or by a `.env` the container reads — and nothing in the binary compares the running environment against the baked value. `BakedEnv` exists as a field on the attestation manifest (`proxy-router/internal/attestation/golden.go:48`) and is referenced nowhere else in the Go tree, so there is no runtime check to fail. The **deployment** does not close it either. A SecretVM measures the compose file, and editing the compose does change the measurement — but the compose declares `env_file: - usr/.env` (`proxy-router/docker-compose.tee.yml:15-16`), and that file's contents are not part of the measured bytes while Docker precedence puts them above the image's `ENV`, so the value can be set there with the attestation unchanged. The manifest does not settle it either: `baked_env.PROXY_STORE_CHAT_CONTEXT` is a workflow literal (`.github/workflows/build.yml:957`), not a value read out of the image. Treat `false` as the default you get, not as a guarantee. See [TEE reference](/providers/full/tee-reference).

## Model health self-checks (provider)

On provider nodes the proxy-router periodically probes every model from `models-config.json` that has an **active bid from this provider**: LLM models get a small dynamically generated arithmetic prompt (correctness is graded), embedding models get an embeddings request, and other model types are skipped. The report covers the whole ecosystem of bids and configured models — active bids whose model is missing from `models-config.json` are flagged as `no_model_configured` (capacity being sold with no backend to serve it). The cached per-model results (on-chain `modelId` and registered model name, `bidId`, status, `errorKind` plus upstream `httpStatus` on failure, `lastHealthy` epoch, latency, prompt correctness — never the private `models-config.json` `modelName`, `apiUrl`, or `apiKey`) are exposed in the `models` field of `GET /healthcheck`, in the `network.ping` (pong) response on the `:3333` MOR RPC port, and in `POST /proxy/provider/ping`, so consumers can see a provider's model health before opening a session. Full operational guide: [Model health self-report](/providers/full/model-health).

| Variable | Default | Notes |
|----------|---------|-------|
| `MODEL_HEALTH_CHECK_DISABLED` | `false` | Set `true` to disable the loop (the `models` field disappears from `/healthcheck`) |
| `MODEL_HEALTH_CHECK_INTERVAL` | `1h` | How often models are probed; results are cached between runs |
| `MODEL_HEALTH_CHECK_TIMEOUT` | `60s` | Per-model probe timeout |
| `MODEL_HEALTH_CHECK_PROBE_DELAY` | `2s` | Pause between per-model probes so many-model providers don't burst their upstream into a rate limit |
| `MODEL_HEALTH_MAX_CONSECUTIVE_ERRORS` | `3` | Consecutive real-session prompt failures after which the model is reported `degraded` when every failure in the streak was a 429 (upstream rate limiting), and `unhealthy` otherwise, with `errorKind: session_errors` in both cases, immediately, without waiting for the next scheduled probe |

## Session health policy (consumer)

On consumer nodes, `SESSION_HEALTH_POLICY` controls how strictly the pre-open healthcheck pings gate provider selection when opening a session **by model ID** (the failover loop). Opening by a specific bid ID is unaffected.

| Variable | Default | Notes |
|----------|---------|-------|
| `SESSION_HEALTH_POLICY` | `permissive` | One of `permissive`, `preferred`, `strict` — see below |

| Policy | Behavior |
|--------|----------|
| `permissive` | Default, same as previous releases: skip only providers that self-report the bid's model as `unhealthy`, `tee_unverified`, or `no_model_configured`. Providers with an unknown or missing report are still tried. |
| `preferred` | When at least one provider reports the model `healthy` or `degraded`, only those providers are tried and unknown/missing reports are skipped. When none does, the open falls back to `permissive` so the model is not black-holed. |
| `strict` | Only providers that report the model `healthy` are tried. `degraded` and unknown reports are excluded. |

**Single-bid caveat** (`healthPolicySingleBid: permissive`, fixed): when the hard filters (omitted provider, own bids) leave a single candidate provider for the model, `preferred`/`strict` are forced to `permissive` for that open so the sole provider can still be tried — single-provider models must remain usable.

## System tuning (optional sysctl tweaks)

These map to OS-level adjustments and only apply when `SYS_ENABLE=true`.

<Warning>
Optional to **enable**, not optional to **succeed**. With `SYS_ENABLE=true` on Linux or macOS, a `sysctl`/`setrlimit` call the process is not privileged to make aborts startup: `main.go:146-149` logs `failed to apply system config, try using sudo or set SYS_ENABLE to false to disable` and then **returns the error**, so the process exits non-zero. In an unprivileged container this turns a tuning knob into a crash-loop — leave `SYS_ENABLE=false` unless the node runs with the privileges to apply every value. (On Windows `ApplyConfig` is a no-op and always succeeds.)
</Warning>

## Mainnet vs testnet quick switch

Comment / uncomment the appropriate block in `.env`. Each block is **five**
values — the four blockchain settings plus `ENVIRONMENT`, which the sample
`.env` switches alongside them (`proxy-router/.env.example:14-26`):

```bash
# MAINNET
ETH_NODE_CHAIN_ID=8453
DIAMOND_CONTRACT_ADDRESS=0x6aBE1d282f72B474E54527D93b979A4f64d3030a
MOR_TOKEN_ADDRESS=0x7431aDa8a591C955a994a21710752EF9b882b8e3
BLOCKSCOUT_API_URL=https://base.blockscout.com/api/v2
ENVIRONMENT=production

# TESTNET (Base Sepolia)
# ETH_NODE_CHAIN_ID=84532
# DIAMOND_CONTRACT_ADDRESS=0xA328196f2438DADA5ab729E39388D86896c27c85
# MOR_TOKEN_ADDRESS=0x5C80Ddd187054E1E4aBBfFCD750498e81d34FfA3
# BLOCKSCOUT_API_URL=https://base-sepolia.blockscout.com/api/v2
# ENVIRONMENT=development
```

`ENVIRONMENT` is not a chain selector, so leaving it on the mainnet value
does not point the node at the wrong network — but it is the fifth value
[Run with Docker](/consumers/install/docker) tells you to change, and the
sample `.env` pairs it with each block, so switch it with the rest.
