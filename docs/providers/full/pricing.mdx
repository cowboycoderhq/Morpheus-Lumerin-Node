There is **no built-in pricing helper, no order book, and no "always use market price" toggle** for provider bids today. You set `pricePerSecond` (in **wei/sec** of MOR) when you call `postModelBid`, and you adjust it by replacing the bid. This page is the explicit how-to for that workflow.

<Note>
This page is for the **provider** side — pricing for the on-chain bid. Pricing for **consumers** of the [hosted Inference API](/inference-api/overview) is a different layer (per-token billing on top of the marketplace) and is documented at [apidocs.mor.org](https://apidocs.mor.org).
</Note>

## Units and floors

- `pricePerSecond` is denominated in **wei of MOR** (1 MOR = 10^18 wei).
- Floor: `bidMinPricePerSecond = 10000000000` wei/sec on Base mainnet = `0.00000001` MOR/sec ≈ `0.0000006` MOR/min ≈ `0.000036` MOR/hour at the floor.
- On Base Sepolia the floor is not a fixed constant: it is whatever `getMinMaxBidPricePerSecond()` returns, `121052630917` wei/sec as of 2026-08-27. An owner call set that value after the contract was deployed; the number's origin is not recorded — it is not something the deploy performs (`1_full_protocol.migration.ts:105-109` passes the config figure straight through). A redeploy would therefore *not* reproduce it — the floor would come up at whatever `config_base_sepolia.json:7` holds and would have to be set again by its owner. Either way the literal here can be stale, so read it before you bid (see below).
- Ceiling: `bidMaxPricePerSecond`, enforced on chain — `postModelBid` reverts with `MarketplaceBidPricePerSecondInvalid` outside the bounds (`smart-contracts/contracts/diamond/facets/Marketplace.sol:80-84`). Neither network's ceiling has been verified against the chain: read it as the second value returned by `getMinMaxBidPricePerSecond()`, not from a config. The deploy configs are inputs to a future deployment rather than readings — no deploy path reads `config_base_mainnet.json` at all (`deploy/helpers/config-parser.ts:20` hardcodes the Sepolia file), and the Sepolia config's figure was superseded on chain: `setMinMaxBidPricePerSecond(min, max)` is the only writer of either bound and writes **both in one call** (`Marketplace.sol:47-61`), so the owner call that moved the Sepolia floor above necessarily overwrote the ceiling at the same time. No ceiling reading has been recorded for either network (`tools/docs-audit/onchain-params.mjs:116-147`). Within the bounds, rating algorithms and competing bids push consumers away from over-priced bids.

Read the live bounds before you bid — on Base Sepolia the floor is whatever the owner last set, and a redeploy would reset it to the deploy config's figure rather than recompute it, so a literal copied from these docs can be stale:

```bash
cast call <DiamondContract> "getMinMaxBidPricePerSecond()(uint256,uint256)" \
  --rpc-url https://sepolia.base.org     # Base mainnet: https://mainnet.base.org
```

## Step 1 — Look at competing bids

The cheapest reference is the live snapshot of bids the network is actually accepting:

```bash
curl -sS https://active.mor.org/active_bids.json | jq
```

Filter by your model (or one similar in size and capability):

```bash
curl -sS https://active.mor.org/active_bids.json \
  | jq '[.bids[] | select(.ModelName | test("your-model-name"; "i"))] | sort_by(.PricePerSecond | tonumber)'
```

Look at the distribution. **Median competitor pricing** is a sane starting point.

## Step 2 — Estimate your cost floor

```
your_$/sec  ≈  amortised_hardware_$/month
              ÷ utilised_seconds_per_month
              + amortised_electricity_$/sec
              + amortised_bandwidth_$/sec
              + your_target_margin
```

Rough sanity check:

- A `g5.xlarge` on demand on AWS is roughly `$1.00 / hour` ≈ `$0.000278/sec` (a real provider would use spot or self-host, but this is a high bound).
- If `1 MOR ≈ $X` (look up live), then `1 MOR/sec ≈ $X/sec`. Convert your `$/sec` into `MOR/sec` via that rate.
- Convert to wei: `pricePerSecond_wei = MOR_per_second × 10^18`.

For a resale provider, replace hardware cost with **upstream API cost** — e.g. Venice subscription `$X/month` divided by your expected utilised seconds. See [Resale registering-bid](/providers/resale/registering-bid) for the resale math.

## Step 3 — Pick a number, post the bid

```bash
curl -X POST 'http://localhost:8082/blockchain/bids' \
  -H 'Authorization: Basic <base64(user:pass)>' \
  -H 'Content-Type: application/json' \
  -d '{
    "modelID": "0xYOUR_MODELID",
    "pricePerSecond": "10000000000000"
  }'
```

The contract reverts if `pricePerSecond` is below the floor **or above the ceiling** — `Marketplace.sol:80-84` reverts `MarketplaceBidPricePerSecondInvalid` anywhere outside `[bidMinPricePerSecond, bidMaxPricePerSecond]`. That check runs before the bid fee is transferred (`Marketplace.sol:86`), so an out-of-bounds bid costs gas, not stake.

## Step 4 — Watch and adjust

There is no auto-adjust. When a provider calls `postModelBid` for the same provider+model and a previous active bid exists, the contract automatically deletes the old bid in the same transaction (see `Marketplace.sol` nonce > 0 logic). Only one call is needed to update the price, not two separate transactions. The `postModelBid` call still charges the non-refundable `marketplaceBidFee` every time (`0.3` MOR on Base mainnet, live on-chain; `0` on Base Sepolia, where bids are free) (see "How bid posts cost MOR" below). Don't repost more often than you have to.

Things to watch:

- **Bid acceptance rate**. If you get zero sessions over days while competitors with similar specs do, you're priced too high.
- **Provider reputation signals**. Even at the right price, low uptime / poor TTFT / failed sessions tank your match rate. See the [reputation system](/concepts/architecture#reputation-and-provider-selection).
- **Active rate from `active_bids.json`**. If your bid disappears from the snapshot, your `:3333` is no longer reachable to the verifier — see [verify-setup](/providers/full/verify-setup).

## How bid posts cost MOR

Every time you call `postModelBid`, the marketplace charges a non-refundable **`marketplaceBidFee`** — `0.3` MOR on Base mainnet and `0` on Base Sepolia, where bids are free. Both are live on-chain readings from `getBidFee()`, not deploy inputs: no deploy path reads `config_base_mainnet.json` (`deploy/helpers/config-parser.ts:20` hardcodes the Sepolia file), and `config_base_sepolia.json` still lists `300000000000000000`, which the live Sepolia contract does not charge. It is **not a constant**: `setMarketplaceBidFee` is `onlyOwner` ([`Marketplace.sol:40`](https://github.com/MorpheusAIs/Morpheus-Lumerin-Node/blob/main/smart-contracts/contracts/diamond/facets/Marketplace.sol)), so check the deployed value before budgeting. This fee is **separate from**, and on top of:

- the refundable **provider stake** (`0.2` MOR on Base mainnet — live on-chain value, `0.2` on Sepolia) you posted at registration,
- the refundable **model stake** (`0.1` MOR) you posted when registering the model,
- BASE gas (paid in ETH on BASE).

If you post → tweak → post → tweak → … six times during configuration, you've paid `~1.8 MOR` on Base mainnet in non-refundable bid fees, plus gas. On Base Sepolia those same six posts cost `0` in fees, because the Sepolia bid fee is zero — only gas applies. That's the most common reason new providers report losing MOR during setup: **it wasn't slashed, it was bid fees**. See also [Quickstart → "What can cost you MOR during setup"](/providers/full/quickstart#what-can-cost-you-mor-during-setup).

## What about "stake-for-liquidity" rewards?

That's a **different product** — the Capital Contract / stake-for-liquidity program documented at [mor.org](https://mor.org). It is **not** the same as provider session payouts and is unrelated to your bid pricing decisions. Your provider stake bonded at registration is **not** the same as staking in the Capital Contract. See [Tokens and fees](/concepts/tokens-and-fees) for the distinction.

## What you can't do today

The chat history surfaces a few asks that **do not have a solution yet**:

- ❌ "Always use market price" toggle. You set the rate manually.
- ❌ Token-level pricing (input vs output, context size). Provider-side pricing is `wei/sec` only.
- ❌ Built-in pricing recommender. Use `active_bids.json` and your own cost model.

If/when these land, this page is where it'll be documented.
