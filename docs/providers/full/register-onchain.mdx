After your proxy-router is running, register on the BASE Diamond contract. **Prefer looking up an existing model and posting a bid on it** — minting a new model for every provider floods the marketplace with duplicate names.

<Note>
**Preferred operator UI:** [MyProvider](https://myprovider.mor.org) ([guide](/providers/full/myprovider-gui)) — especially on SecretVM, where the node already serves HTTPS. Swagger at `http://localhost:8082/swagger/index.html` (or `https://<your-node>/swagger/`) remains the API fallback — click **Authorize** and use your `.cookie` / `COOKIE_CONTENT` credentials before **Try it out** ([API auth](/reference/api-auth)).
</Note>

## Contract minimums

| Item | Value (wei) | Display |
|------|-------------|---------|
| `providerMinStake` | `200000000000000000` (Base mainnet) · `200000000000000000` (Base Sepolia) | `0.2` MOR · `0.2` MOR — `getProviderMinimumStake()` readings of 2026-08-31, below |
| `modelMinStake` | `100000000000000000` (both) | `0.1` MOR |
| `marketplaceBidFee` | `300000000000000000` (Base mainnet) · `0` (Base Sepolia) | `0.3` MOR · `0` — Base Sepolia bids are free; `getBidFee()` readings of 2026-08-31, below; owner-settable via `setMarketplaceBidFee`, so re-read before budgeting |
| `bidMinPricePerSecond` | `10000000000` (Base mainnet — the deploy input is named `marketplaceMinBidPricePerSecond`; note that **no deploy path reads `config_base_mainnet.json`** — `deploy/helpers/config-parser.ts:20` hardcodes `deploy/data/config_base_sepolia.json` for every migration — so check the deployed contract for the live bound) | `0.00000001` MOR/sec — on Base Sepolia read `getMinMaxBidPricePerSecond()` for the live floor, `121052630917` wei/sec as of 2026-08-27; both bounds are owner-settable |

<Note>
**Read from the deployed contracts on 2026-08-31.** These are readings, not deploy
inputs. Read-only `eth_call` against each network's Diamond:

| Network | Block | `getBidFee()` | `getProviderMinimumStake()` |
|---------|-------|---------------|-----------------------------|
| Base mainnet (chain `8453`) | `50701626` | `300000000000000000` = `0.3` MOR | `200000000000000000` = `0.2` MOR |
| Base Sepolia (chain `84532`) | `46212156` | `0` — bids are free | `200000000000000000` = `0.2` MOR |

`config_base_mainnet.json:4,6` agrees with both mainnet readings. On Base Sepolia
the stake agrees and **the bid fee does not**: `config_base_sepolia.json:6` lists
`300000000000000000` where the chain returns `0`. The chain is the authority, so
the config is the stale artifact and the pages saying Sepolia bids are free are
correct.

Why the config drifted, from git history: `906bb602` re-pointed
`lumerinProtocol` at a different Diamond, changing only `fundingAccount`,
`lumerinProtocol` and `owner`. `setMarketplaceBidFee` is the sole writer of the
stored fee (`Marketplace.sol:40-45`) — `__Marketplace_init` (`:29-38`) never sets
it, and only `1_full_protocol.migration.ts:117` calls it, on a protocol that
migration deploys. Nothing applied it to the Diamond the config was re-pointed
at, so `bidFee` sits at its storage default of zero.

Both values are owner-settable and can change without a commit. Treat the block
numbers as the expiry date on these figures and re-read before budgeting.
</Note>

## Step 0 — Look up models before you mint

Browse [active.mor.org/status](https://active.mor.org/status) or pull the JSON snapshots:

| URL | Use |
|-----|-----|
| [active_models.json](https://active.mor.org/active_models.json) | Routable models (healthy/degraded bids) — start here |
| [active_bids.json](https://active.mor.org/active_bids.json) | Competing `pricePerSecond` for a model name |
| [all_models.json](https://active.mor.org/all_models.json) | All non-deleted on-chain models (including ones with no live healthy provider) |
| [status](https://active.mor.org/status) | Human UI + uptime / min price views |

```bash
# Find a model by name. Top-level model fields are PascalCase (Name, Id, Tags, Owner);
# the nested objects are not — `health` and `bidDetail` are lowercase, and bidDetail
# entries use camelCase (providerId, pricePerSecond).
curl -sS https://active.mor.org/active_models.json \
  | jq '.models[] | select(.Name | test("llama-3.3"; "i")) | {Name, Id, IpfsCID, Tags, Owner, health}'

# Competing bids for that name
curl -sS https://active.mor.org/active_bids.json \
  | jq '[.bids[] | select(.ModelName | test("llama-3.3"; "i"))] | sort_by(.PricePerSecond | tonumber) | .[:5] | .[] | {ModelName, Provider, PricePerSecond, Id}'
```

**Decision rule:**

| Situation | What to do |
|-----------|------------|
| Same logical model already listed (same weights / name you intend to serve) | **Do not create a model.** Register as a provider, then **bid on that existing `Id`**. Put that `Id` in `models-config.json`. |
| You need a `tee` tag and no suitable `tee`-tagged model exists | Register a **new** model with tag `tee`, then bid. |
| Genuinely new weights, fine-tune, or metadata | Register a **new** model (new `ipfsCID` / name), then bid. |

Any registered provider can bid on any active model — you do **not** need to own the model record. Creating another model with the same display name still adds a separate marketplace entry and is what produces the duplicate clutter on [active.mor.org](https://active.mor.org).

      </Step>

      </Step>
    </Steps>
  </Tab>
  <Tab title="Swagger / API">
    <Steps>
      <Step title="Authorize the Diamond contract">
        `POST /blockchain/approve` — set `spender = <DiamondContract>` and `amount` (in **base units**, 18 decimals — it is passed to `approve` unscaled, `service.go:1047`) ≥ enough MOR for provider stake + (optional) model stake + bid fee. Bidding on an existing model needs provider stake + the `marketplaceBidFee`: on **Base mainnet** `0.2` + `0.3` = **≈ `0.5`** MOR, on **Base Sepolia** `0.2` + `0` = **`0.2`** MOR (the Sepolia bid fee is zero). Minting a new model adds `0.1` MOR model stake (**≈ `0.6`** mainnet — `0.2` + `0.3` + `0.1`; **`0.3`** Sepolia — `0.2` + `0` + `0.1`).
      </Step>
      <Step title="Register your provider">
        `POST /blockchain/providers` — set `stake` (≥ `0.2` MOR on Base mainnet, `0.2` on Sepolia; there is no subnet tier — a single `providerMinimumStake` applies to every provider) and `endpoint` (your **publicly accessible** `host:port`, no protocol).
      </Step>
      <Step title="Post a bid on an existing model (preferred)">
        From Step 0, take the model's `Id`. `POST /blockchain/bids` with that `modelID` and `pricePerSecond` (≥ `10000000000` on Base mainnet; on Sepolia, ≥ whatever `getMinMaxBidPricePerSecond()` returns — `121052630917` as of 2026-08-27). Put the same `Id` in `models-config.json` and restart the proxy-router. Capture the returned `bidID`.
      </Step>
      <Step title="Only if needed — create a new model">
        `POST /ipfs/add` (and `POST /ipfs/pin`) for a real CID when you have one, then `POST /blockchain/models` with:
        - `id`: optional random 32-byte hex (base id; the on-chain id becomes `keccak256(owner ‖ baseId)`). Omit it and one is generated.
        - `ipfsID`, `fee`, `stake` (`0.1` MOR min), `name`, `tags`. There is no `Owner` field — the owner is the signing wallet.
        - `tags` **must include a type tag** or the request is rejected with 400: one of `llm`/`textgeneration`/`text2text`/`t2t`, `stt`/`transcribe`/`s2t`/`speech`, `tts`/`text-to-speech`, or `embedding`/`embeddings` (`model_tags.go:20-35`). TEE providers add `"tee"` **in addition** (case-insensitive). Note the router's 400 message names `chat`, which is not an accepted tag.
        Capture the response `modelID` (combined id) for `models-config.json` and the bid.
      </Step>
      <Step title="Update models-config.json">
        Map the on-chain `modelID` you bid on to your backend `apiUrl`. Restart the proxy-router. See [models-config.json](/reference/models-config).
      </Step>
    </Steps>
  </Tab>

## TEE tag deeper context

Tagging the model `tee` engages two independent verifications on every session and prompt — one each side:

- **Phase 1 (consumer → your P-Node).** Any v6.0.0+ consumer proxy-router will verify your P-Node's TDX attestation (CPU quote, TLS pinning, RTMR3 of the `-tee` image) at session open and on every prompt before forwarding inference.
- **Phase 2 (your P-Node → backend).** Your v7.0.0+ P-Node will verify the backend LLM your model's `apiUrl` points to — CPU TDX quote, TLS pinning, RTMR3 replay of the backend's `docker-compose.yaml`, CPU-GPU nonce binding, and NVIDIA NRAS GPU attestation — at startup and on every prompt.

A v6+ consumer benefits from Phase 2 automatically by trusting your attested v7+ P-Node — no client-side upgrade needed. Models without the `tee` tag are treated as standard providers; neither hop runs.

If you **bid on someone else's model**, you inherit that model's tags. To offer TEE attestation to consumers, bid on an existing `tee`-tagged model or register your own with `"tee"`.

See [TEE overview](/concepts/tee-overview) and [TEE reference](/providers/full/tee-reference).

## Pausing or temporarily disabling a model offering

To stop offering a model **without deregistering it** (so you keep any model stake bonded and can resume):

```bash
# Find your active bid
curl -sS -u 'admin:admin' \
  'http://localhost:8082/blockchain/providers/0xYOUR_PROVIDER/bids/active' \
  | jq '.bids'

# Delete the bid
curl -X DELETE -u 'admin:admin' \
  'http://localhost:8082/blockchain/bids/0xYOUR_BID_ID'
```

The model record stays on chain. To resume, post a new bid (which charges the `marketplaceBidFee` again — `0.3` MOR on Base mainnet; on Base Sepolia the fee is `0`, so reposting there costs only gas; see [pricing](/providers/full/pricing)).

If you **own** a model and want to **completely remove** it: delete all of its bids first, then call `modelDeregister` to recover the `0.1 MOR` model stake. The contract refuses `modelDeregister` while any bid for that model is still active. If you only ever bid on someone else's model, deleting your bid is enough — you have no model stake to recover.

## How and when you get paid

For typical staked sessions, the protocol pays you **inside `closeSession`** via `_rewardProviderAfterClose`, with the funds coming from a **separate protocol `fundingAccount`** (via `transferFrom`), not from the consumer's stake in real time. There is no separate "session claim" step for the standard flow — the payment for time actually used hits your provider wallet in the same transaction that closes the session.

What this means for you operationally:

- Keep your provider wallet ready to **receive** MOR; you don't need to call a claim function in the standard flow. The exception is an **early close with a dispute** — `_rewardProviderAfterClose` withholds part of that session's reward, and you release it later with `claimForProvider(sessionId)` (see [Rewards and economics](/concepts/rewards-and-economics)).
- For the **direct-payment** carve-out (a separate flow some sessions use), behavior differs — see the contract source and [tech.mor.org/session.html](https://tech.mor.org/session.html) for the canonical breakdown.
- If `closeSession` ever fails because the protocol funding account is empty or under-approved, **no provider gets paid until operators top it up** — that's a network-wide failure mode, not a per-provider one.
